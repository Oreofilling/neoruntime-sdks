### 未修复:竖屏 stride 不匹配(发现 #4,本报告全部 ERROR 的共同根因)

- **现象**:main/sub 流取帧解码抛 `ValueError: cannot reshape array of size 13271040 into shape (5760,2160)` / `1474560 into (1920,720)`(`frame.py:614 _decode_raw`);third 流(384 宽,天然对齐)正常。
- **根因**:楔死窗口中的 `set_transform(rotation=1)` 竖屏几何在设备重启后仍生效(main 2160×3840、sub 720×1280)。daemon fd publisher 按**对齐后宽度 stride** 下发 NV12(sub 实际 1,474,560 B = 768×1280×1.5;main 13,271,040 B = 2304×3840×1.5),而线上头部携带**逻辑宽度**(720/2160),SDK `_decode_raw` 按紧排布 reshape → 尺寸失配。初测横屏窗口宽度 3840/1280 恰好对齐、缓冲即紧排,故未暴露。
- **归因**:daemon 侧暴露 stride 化缓冲 + SDK 侧紧排假设,两侧各占一半;修复方向为线上头部携带 stride 或 SDK 按 stride 解包,待与平台侧对齐。本报告 5 个 ERROR(toolkit 3 处 + 录制/Web 2 处)全部源于取不到可解码的 main/sub 真帧,无独立新缺陷。
- **处置**:不回调 `set_transform` 复原横屏 —— 该调用正是本次 camera-daemon 楔死的触发点(见「环境事件与恢复记录」),设备保持竖屏几何。

### subscribe: frames arrive but every inference fails -2814 (HAL_ERR_INVALID_ARG) on the deployed ai-runtime build, even with a geometry-matched stream/model pair (probed 2026-09-09); SDK raises RuntimeError after 10 consecutive failed frames

> **已解决(2026-09-10)**:根因在 ai-runtime 侧而非 HAL——StreamInfer 旧代码构造 `data=nullptr` + 裸 dma_fd 的输入张量,而 HAL v2 只收 CPU 指针输入(`!in.data` → HAL_ERR_INVALID_ARG),输入 dma_fd 从不被读。修复:StreamInfer 将 daemon 供帧重打包为紧致 NV12 CPU 缓冲并绑定单个 CPU 张量(与 Infer buffer_id 路径字节同构)。同机复验:几何匹配的 subscribe 恢复出结果,单帧路径与本报告其余项不受影响。新边界:模型输入几何须与流几何一致(否则逐帧 -2811=HAL_ERR_INVALID_SIZE,SDK 10 连败熔断)。以下 9/9 记录保留为当时部署态的历史事实。

影响 2 个用例:InferenceClient.subscribe, InferenceResult.count_by_label/get_objects_by_label
